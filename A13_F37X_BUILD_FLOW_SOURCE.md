# Stage 2N-A13 F37X target-build canonical source audit

This note records the local source audit used to prepare the A13 server build.
It does not claim that any server command, VU37P implementation, XO/xclbin
build, XRT Host execution, or FPGA operation has run in this workspace.

## 1. How the existing RTL kernel is packaged into an XO

The recovered canonical flow is A10 v2:

1. `tcl/package_stage2n_a10_xo_v2.tcl` adds the canonical RTL in dependency
   order and selects `dlrm_f37x_rtl_kernel_stage2n_a10_v2` as top.
2. `ipx::package_project` creates a user IP with inferred `ap_clk`,
   `ap_rst_n`, and `s_axi_control` interfaces.
3. The Tcl adds the AXI4-Lite register descriptions to `component.xml`, marks
   the core as `sdx_kernel` / `rtl`, and calls `package_xo` with
   `-ctrl_protocol user_managed`.
4. `package_xo` produces both the XO and `kernel.xml`; the canonical flow does
   not maintain a handwritten kernel XML.

A13 follows the same mechanism in
`scripts/package_stage2n_a13_rtl_kernel_v1.tcl`. It preserves all 77 A10 v2
component registers and appends four read-only registers at `0x218`, `0x21C`,
`0x220`, and `0x224`. The expected A13 counts are 81 component registers and
78 kernel arguments; the legacy `CONTROL_STATUS`, `VERSION`, and
`RESULT_COUNT` remain component-only exactly as in A10.

## 2. Which Tcl is canonical

- A8 recovery identified `tcl/package_stage2n_a8_a7_xo_v3.tcl` as the
  canonical A7-kernel packager, but its old v3 wrapper runner was explicitly
  excluded because of an obsolete post-check.
- The capacity-expanded design uses the later, internally consistent
  `tcl/package_stage2n_a10_xo_v2.tcl` plus
  `scripts/run_stage2n_a10_xo_package_v2.sh`.
- A10 non-v2 RTL/TB/Tcl and A8 v1/v2 packagers are historical or superseded
  and are not A13 sources.
- A13 uses the new `scripts/package_stage2n_a13_rtl_kernel_v1.tcl`; no A13 RTL
  or TB was changed to create it.

## 3. Where kernel.xml comes from

`kernel.xml` is generated by Vivado `package_xo -output_kernel_xml`. There is
no canonical source-controlled kernel XML to copy or edit. A13 therefore does
not add a handwritten XML file. The package and aggregate scripts validate the
generated kernel name, AXI-Lite interface, register count, and four counter
offsets before linking.

## 4. Platform and target part

The A10 canonical link script uses the platform file:

`/opt/xilinx/platforms/inspur_f37x_xdma_201920_3/inspur_f37x_xdma_201920_3.xpfm`

The platform VBNV is `inspur_f37x_xdma_201920_3`; the inherited target part is
`xcvu37p-fsvh2892-2L-e`. The requested kernel clock remains 100 MHz. These
paths and the actual server-installed Vivado/Vitis/XRT versions are inputs to
be verified on the server by the user; they were not accessed locally.

## 5. How the compute unit is defined

A10 linked one instance with:

`--connectivity.nk dlrm_f37x_rtl_kernel_stage2n_a10_v2:1:dlrm_a10_1`

The A13 equivalent is recorded in `config/stage2n_a13_v1.cfg`:

`nk=dlrm_f37x_rtl_kernel_stage2n_a13_v1:1:dlrm_a13_1`

This keeps one kernel instance and one CU. The full runtime IP name compiled
into the existing A13 Host is
`dlrm_f37x_rtl_kernel_stage2n_a13_v1:dlrm_a13_1`, so the config and Host agree.

## 6. Design/connectivity configuration

The recovered A10 flow supplied connectivity on the `v++ --link` command line
and did not contain a source-controlled cfg. A13 adds the smallest equivalent
cfg containing only `[connectivity] nk=...`. Platform, target `hw`, 100 MHz,
jobs, implementation strategy, and physical optimization settings remain
explicit command-line arguments in `scripts/build_stage2n_a13_target_v1.sh`,
matching the canonical A10 link semantics.

The authoritative target timing result is the routed Vitis platform design.
`scripts/report_stage2n_a13_vitis_post_route_v1.tcl` opens that routed
checkpoint and generates timing, utilization, DRC, methodology, check-timing,
RAM, and high-fanout evidence. The optional
`scripts/run_stage2n_a13_target_vu37p_v1.tcl` is an exact-part standalone
diagnostic only and is explicitly not the F37X platform timing gate.

## 7. HBM/DDR binding

There is no binding. The A13 top has only `ap_clk`, `ap_rst_n`, and the
`s_axi_control` AXI4-Lite slave. It has no `m_axi` port, memory argument, HBM
lookup, DDR data path, BO, or DMA channel. Consequently the A13 cfg contains no
`connectivity.sp` entry and does not invent an HBM/DDR assignment.

Embeddings remain CPU-resolved data programmed through AXI-Lite registers, the
same architectural boundary as A10/A11/A12.

## 8. Host compiler and XRT link flags

The canonical A11/A12 Host runners compile their C++11 legacy-HAL sources with:

- `g++ -std=gnu++11 -O2 -Wall -Wextra -Wpedantic`;
- include path `${XILINX_XRT}/include`;
- library path and runtime path `${XILINX_XRT}/lib`;
- `-lxrt_core -pthread -ldl`.

`scripts/build_stage2n_a13_host_v1.sh` uses those same flags and requires
`xrt.h`, `experimental/xrt-next.h`, and `libxrt_core.so`. It records expected
XRT release `2.9.210507`. It does not add `xrt_coreutil`, because the canonical
legacy HAL Host uses `xclOpen`, `xclOpenContext`, `xclRegRead`, and
`xclRegWrite`, whose recovered runners link only `xrt_core`. Most importantly,
the build script never executes the produced Host binary.

## 9. Final kernel/CU determination and evidence boundary

- Kernel: `dlrm_f37x_rtl_kernel_stage2n_a13_v1`
- CU: `dlrm_a13_1`
- Runtime IP name: `dlrm_f37x_rtl_kernel_stage2n_a13_v1:dlrm_a13_1`
- Platform: `inspur_f37x_xdma_201920_3`
- Target part: `xcvu37p-fsvh2892-2L-e`
- Requested clock: 100 MHz
- Control protocol: user-managed AXI4-Lite
- Memory masters/bindings: none

A11 and A12 did not introduce a newer FPGA kernel package: their canonical
Host/asset/performance flows reused the already-linked A10 v2 image. Therefore
A10 v2 is the correct packaging/link source for A13, while A11 provides the
Host compiler convention.

Still unresolved until the user runs the package on the server are the actual
server tool paths and exact versions, platform availability, routed WNS/TNS and
failing endpoints, LUT/FF/BRAM/URAM/DSP counts, DRC/methodology findings,
high-fanout paths, XO/xclbin hashes and UUID, and XRT link compatibility.
Complete implementation in the F37X shell, xclbin generation, and board
validation are not claimed by this local preparation.
